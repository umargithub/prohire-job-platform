Why all PKs are UUID, not SERIAL UUID primary keys prevent row-count enumeration (an attacker cannot guess that id=1001 exists by incrementing from a known ID). They also allow safe distributed ID generation without a centralised sequence — important if the app ever shards or generates IDs client-side. PostgreSQL generates them with gen_random_uuid() (cryptographically random, no collision risk at scale).
ON DELETE CASCADE everywhere Every foreign key uses ON DELETE CASCADE. Deleting a user automatically removes their company, all jobs, all applications, and all tokens. No application code has to orchestrate multi-table deletes. PostgreSQL's constraint system guarantees referential integrity even if a bug skips the service layer.
users → applications — two FK paths The applications table has two foreign keys into users: one through jobs → companies → users (the company owner) and one directly via candidate_id. This means deleting a user cascades both as a company owner (removing all their job listings and applications to those jobs) and as a candidate (removing all their own application records).
applications.version — Optimistic Locking Column The version INTEGER NOT NULL DEFAULT 1 column on applications is reserved for Phase 7 (optimistic locking for stage transitions). When a company updates an application's stage, the UPDATE includes WHERE version = $expected and increments version on success. A missed update (0 rows affected) signals a concurrent write.

Why three separate token tables instead of one? A single tokens table with a type column would work, but separate tables make it impossible to accidentally use a verification token as a refresh token at the query level — you'd have to explicitly query the wrong table. It also allows adding table-specific columns later (e.g. a device_name on refresh tokens) without null pollution.
token_hash — never store raw tokens Every token table stores a SHA-256 hash of the raw token, not the raw token itself. Raw tokens live in HTTP-only cookies or email links. A DB breach exposes only hashes — pre-image resistance means an attacker cannot reverse them into usable tokens.
Indexes chosen for query patterns, not just FKs The jobs table has 4 indexes: company_id (owner lookups), is_active (candidate browsing filter), job_type and experience_level (Phase 5 filters). Each index was added because a specific query pattern needs it — not speculatively.
TIMESTAMPTZ, not TIMESTAMP All timestamp columns use TIMESTAMPTZ (timestamp with time zone). PostgreSQL stores these as UTC internally and converts on read. Using plain TIMESTAMP would store wall-clock time without a timezone, making daylight saving transitions ambiguous.

Global Rate Limiter (all routes) A sliding-window rate limiter of 500 requests per 60 seconds is applied at the Express app level before any route. It uses the same Redis Lua atomic script as the auth-specific limiters, keyed by prohire:rate_limit:global:<ip>. This is the last line of defence against floods even on unauthenticated endpoints.
Anti-Enumeration on /forgot-password and /resend-verification Both endpoints always return 200 with the same message regardless of whether the email exists and regardless of whether an email was actually sent. This prevents an attacker from probing which email addresses are registered.

POST /api/v1/auth/refresh
200 OK 401 INVALID_TOKEN
chain: rate limit — none → validate — none → asyncHandler
Request
No body.
Cookie: refreshToken=<rawToken>  // sent automatically by browser
200 Response + new Set-Cookie
{
  "success":     true,
  "accessToken": "eyJ...",
  "user": { "id": "uuid", "email": "...", "role": "..." }
}
// Old cookie cleared, new refreshToken cookie set (7d)
Token rotation on every refreshThe old refresh token row is deleted and a new one is inserted atomically. A stolen refresh token can only be used once — the next legitimate refresh will fail and expose the theft.
