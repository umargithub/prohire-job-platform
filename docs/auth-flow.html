Architecture Rule Controllers are thin — they only extract a validated DTO, call one service method, and return JSON. All business logic lives in AuthService. All SQL lives in AuthRepository. No cross-module repository imports. Services may call other services.
Error Propagation Services throw typed AppError subclasses. asyncHandler catches any thrown error and forwards it to the global error handler middleware, which formats the response. Stack traces are never exposed in production.

Performance Decision — Email Check Before Hash findByEmail runs before bcrypt.hash. bcrypt at 12 rounds costs ~300 ms of CPU. Checking the email first means duplicate-email rejections are fast (single DB query) without burning CPU on a hash that will never be stored.
Atomicity — Single Transaction createUserWithVerificationToken opens one db.transaction() that inserts both the users row and the verification_tokens row. If the server crashes between the two inserts, neither row persists — preventing an orphaned user with no verification token. The email is enqueued after the transaction commits.

Anti-enumeration — Identical Error for Missing User vs Wrong Password Both "user not found" and "wrong password" throw UnauthorizedError("Invalid credentials"). An attacker cannot distinguish between a non-existent account and a wrong password from the response.
Verification Check Order The password is verified before checking is_verified. This prevents an attacker from learning that an email is registered-but-unverified by probing with arbitrary passwords — they must supply the correct password first.

Hash-Then-Lookup Pattern The raw token from the URL is never stored. On receipt, it is hashed with SHA-256 and the hash is used to query the DB. This means a DB breach exposes only hashes — an attacker cannot derive the raw token needed to use them.
Token Consumed on Use deleteVerificationToken removes the token immediately after verification. The same link cannot be used twice.

Rotation Order — Delete Before Insert The old token is deleted before the new one is inserted. This is intentional: if the insert fails, the user is logged out (must re-authenticate) rather than having a dangling old token that can't be rotated. Safety over convenience.
JOIN in findRefreshToken — No Second Query Needed findRefreshToken JOINs users to fetch email and role in the same query. This avoids a second round-trip to look up the user by user_id at rotation time — the RefreshTokenRow type includes those fields.

Token Consumed Before Password Update deletePasswordResetToken runs before updatePassword. If the password update fails, the token is already consumed — the user must request another reset. This prevents the same token from being replayed if an error occurs mid-flow.
No Rate Limiter on This Endpoint Tokens are single-use (deleted on first use) and expire in 1 hour. A brute-force attack on a reset token is impractical — the 32-byte random token has 256-bit entropy. A rate limiter here would add operational friction (e.g., on mobile networks with shared IPs) for no real security gain.

Why token_hash — not the raw token? The raw token (32 bytes of crypto random) is sent to the user via email or cookie. Only the SHA-256 hash is persisted in the database. This provides pre-image resistance: even if the token_hash column is leaked in a DB breach, an attacker cannot reverse-engineer the raw token. The hash is useless without the input.
Why expires_at > NOW() always in WHERE? Expired tokens are not deleted eagerly. Instead, every lookup filters them out with AND expires_at > NOW(). Stale rows eventually accumulate but do no harm. A scheduled cleanup job (Phase 8) will purge them. This avoids contention on high-write paths.
Why role is CHECK-constrained at the DB level? role TEXT NOT NULL CHECK (role IN ('candidate', 'company', 'admin')) — the constraint lives in the database, not just in the application layer. Even if a bug bypasses the service-layer validation, the DB will reject an invalid role. Defence in depth.
Why findRefreshToken JOINs users? refresh_tokens only stores user_id. At token rotation time, the new access token needs email and role from the users table. The JOIN fetches all needed data in one round-trip, so RefreshTokenRow carries email and role fields.
ON DELETE CASCADE on all foreign keys All token tables declare REFERENCES users(id) ON DELETE CASCADE. Deleting a user automatically removes all their tokens — no manual cleanup code needed for account deletion.

Lifecycle annotation — what each stop does and does NOT do

Stop What it does What it does NOT do On failure
Express Router Matches HTTP method + path. Selects the middleware array for that route. Runs no middleware itself — it only dispatches. 404 before any middleware if no route matches.
Rate Limiter redis.eval(Lua) — atomic sliding window. Sets X-RateLimit-* headers on every allowed request. Does not touch req.body or validate anything. Calls next(new AppError(429)) → jumps straight to global error handler, skipping all remaining middleware.
validate() schema.safeParse(req.body). On success, replaces req.body with the parsed, type-safe DTO object, then calls next(). Does not call next(err) on failure — it sends the response directly. Sends 422 VALIDATION_ERROR with field-level error array immediately. Chain stops here.
asyncHandler Wraps the controller function: Promise.resolve(fn(req,res,next)).catch(next). Any throw inside the controller or any service/repo it calls is caught and forwarded. Does not execute any logic itself — it is only an error boundary. Forwards thrown error to global error handler via next(err).
Controller fn Casts req.body to DTO type. Calls one service method. Writes JSON response and status code. No business decisions. No SQL. No direct DB or Redis access. Throws a typed AppError subclass from the service — propagates up through asyncHandler.
Service All business logic: checks, decisions, hashing, JWT generation, BullMQ enqueue. No req/res access. No direct SQL. Never imports db directly. Throws typed AppError subclasses (ConflictError, NotFoundError, etc.).
Repository All parameterised SQL. Opens and manages transactions. Returns typed row objects. No business decisions. Does not call other repositories. Let DB errors propagate — service catches code === '23505' unique-violation if needed.
Global Error Handler The 4-argument (err, req, res, next) middleware registered last in app.ts. AppError subclasses → formatted JSON. Unknown errors → 500. Never exposes stack traces in production. —
Why validate() sends the response directly instead of calling next(err) Validation failures are not exceptional — they are expected user errors. Sending 422 directly avoids routing through the global error handler and keeps the error format consistent and predictable for clients. The global handler is for unexpected errors and thrown AppErrors.

Section 2 — DTOs: when to create one and why

The Rule Create a DTO (Zod schema + z.infer<> type) whenever the request has a body that needs validation — regardless of how many fields. One field still gets a DTO. Route params, query params, and cookies are read directly; they do not get DTOs.

DTO decision table — every auth endpoint

Endpoint Input source DTO? Reason
POST /register/candidate req.body — email, password ✓ RegisterCandidateDto Body needs Zod validation (format + constraints)
POST /register/company req.body — email, password, companyName ✓ RegisterCompanyDto Body needs Zod validation
POST /login req.body — email, password ✓ LoginDto Body needs Zod validation
GET /verify-email req.query.token — single string ✗ — read directly Single query param; read as req.query['token'] as string. No validate() middleware applied.
POST /refresh req.cookies.refreshToken ✗ — read directly Comes from an httpOnly cookie, not the body. No validate() middleware needed.
POST /logout req.cookies.refreshToken ✗ — read directly Same — cookie value, not a body.
POST /forgot-password req.body — email ✓ ForgotPasswordDto Even one field gets a DTO — Zod validates email format and the inferred type flows into the service signature.
POST /reset-password req.body — token, password ✓ ResetPasswordDto Body needs Zod validation
POST /resend-verification req.body — email ✓ ResendVerificationDto Body needs Zod validation (one field — same reasoning as forgot-password)
Why a single-field body still gets a DTO email: z.string().email() validates format — you cannot do that with TypeScript alone. The inferred type z.infer<typeof ForgotPasswordDto> flows into the service method signature, giving you end-to-end type safety from HTTP body to DB call. Consistency matters too: every body = a DTO, no exceptions to remember.

Section 3 — TypeScript types: what belongs at each layer

Two type files, two distinct concerns

File What it defines Direction Used by
auth.dto.ts Zod schemas + z.infer<> types for request input (e.g. RegisterInput, LoginInput) HTTP → app (incoming) Controller casts (req.body as RegisterInput) and service method parameter types
auth.types.ts Interfaces for database rows with snake_case fields (e.g. UserRow, TokenRow, RefreshTokenRow) DB → app (outgoing from DB) Repository generics: db.query<UserRow>(...). Maps 1-to-1 to column names.

Layer-by-layer type ownership

Layer Types it uses Types it defines Notes
Controller DTO input types from auth.dto.ts None const body = req.body as RegisterInput. No new types defined here.
Service DTO input types as method params; Row types indirectly via repository return values None (usually) Service return types are annotated inline. Only add a separate interface if the shape is reused in 2+ places.
Repository Row types from auth.types.ts as the generic on db.query<T> None — Row types live in auth.types.ts, not in the repo file db.query<UserRow>('SELECT ...', [...]) — TypeScript knows the shape of rows[0].
Key insight — RefreshTokenRow extends TokenRow findRefreshToken JOINs the users table to get email and role in one query. So RefreshTokenRow extends TokenRow and adds those two fields. Without the JOIN you'd need a second query and a separate user lookup — more types, more round-trips, more code. The extended type makes the JOIN explicit and self-documenting.
General rule for adding types If a thing comes from the DB → it needs a Row type in *.types.ts. If a thing comes from the HTTP body → it needs a Zod DTO in *.dto.ts. If a service method returns a shape only it uses → annotate the return type inline, no extra interface.

Section 4 — Module boundaries: controller / service / repository

What each layer owns — hard rules

Layer Owns Never touches
Controller HTTP in/out (req/res), DTO extraction, status codes, cookie writes Business logic, SQL, direct DB/Redis access, decisions
Service All business logic and decisions (check this, validate that, combine two things) SQL, req/res, direct DB access — never imports db directly
Repository All SQL, parameterised statements, transaction management Business decisions, HTTP, calling other repositories

Concrete decision rules — how to know which layer a piece of logic belongs to

Question you ask Answer → where it goes
"Does this need an HTTP endpoint?" You need a controller method for it. One method per endpoint.
"Is there a business decision here?" (check a condition, combine data from two places, apply a rule) Service. Even if the decision is one line — it belongs in the service.
"Does this touch the database?" Repository method. One repository method per distinct query or write.
"Do two service methods need the same SQL query?" One repository method called from both. Never duplicate SQL in two repos.
"Does Service A need data that Service B already knows how to fetch?" Service A injects Service B and calls it. Never repository A calls repository B.
"How do I decide what counts as a module?" One business domain = one module. Auth, Jobs, Companies, Applications, Admin are the five modules in ProHire.
When a module might have no repository If a module only coordinates other services and never writes to the DB directly (e.g. a future notification service that only enqueues BullMQ jobs and delegates data fetching to other services), its service layer has no repository. The rule is: no SQL = no repository needed for that module.
How to replicate this pattern in a new module (e.g. Phase 4 — Jobs) 1. Create modules/jobs/ with job.types.ts, job.dto.ts, job.repository.ts, job.service.ts, job.controller.ts, job.routes.ts. 2. Register all three layers in app.ts container (repository → service → controller). 3. Mount routes in app.ts under /api/v1/jobs. 4. Apply validate() middleware at the route level for any endpoint with a body. The middleware chain, DI wiring, and layer responsibilities are identical to the auth module.
