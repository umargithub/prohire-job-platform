Architecture Rule Controllers are thin — they only extract a validated DTO and route params, call one service method, and return JSON. All business logic (cache lookups, ownership checks, cache invalidation) lives in CompanyService. All SQL lives in CompanyRepository. No cross-module repository imports.
No Rate Limiting on Company Endpoints Unlike the auth module, company endpoints carry no per-IP rate limits. They are protected instead by requiring a valid JWT (authenticate) with role = 'company' (authorize). A global rate limiter (500 req/min) is applied at the Express app level and covers all routes.
Error Propagation Services throw typed AppError subclasses (NotFoundError, ConflictError). asyncHandler catches any thrown error and forwards it to the global error handler middleware, which formats the JSON response. Stack traces are never exposed in production.

Cache-Aside Pattern (getOrSet) The service calls getOrSet(key, TTL.COMPANY_PROFILE, fetchFn). On a cache hit, the DB is never queried. On a miss, the fetch function runs, the result is written to Redis, and the data is returned. TTL is 300 seconds (5 minutes), defined as a named constant in ttl.constants.ts — never hardcoded inline.

Write-Through: Invalidate, Never Update in Place On every mutation the cache key is deleted (not overwritten). The next GET request will repopulate it from the DB. This avoids stale-read bugs where the cache holds an old version of the profile after a field is changed.

resolveCompany — Ownership Gate Every job operation first calls resolveCompany(userId) to look up the company by owner_id. This enforces that the requesting user owns the company before any job query runs. It also provides company.id needed for all job queries. If no profile exists, the operation fails with 404 before touching the jobs table.
Salary Cross-Field Validation CreateJobDto includes a Zod .refine() that enforces salary_max >= salary_min. The same constraint is also declared at the DB level as a CHECK constraint — both layers catch it independently.

Ownership Enforced in SQL The query uses WHERE id = $1 AND company_id = $2. A company can only retrieve jobs that belong to them — a job owned by a different company returns null and triggers NotFoundError. No need for a separate ownership check in the service.
Longer TTL for Job Detail Job detail is cached for 600 seconds (10 minutes) vs 300 seconds for the job list. Single-item lookups are more expensive to invalidate precisely, so a longer TTL is acceptable. Both the PUT and DELETE endpoints invalidate prohire:job:{jobId} on write.

COALESCE — Partial Update Without Overwriting UpdateJobDto makes every field optional. The SQL uses COALESCE($n, column) so fields absent from the request body keep their current DB value. No field is accidentally nulled out when the client only updates one or two fields.
Dual Cache Invalidation A job update invalidates two keys: the individual job detail (prohire:job:{jobId}) and the company job list (prohire:company:jobs:{company.id}). Both must be busted because the list returns the full JobRow objects and would otherwise serve stale data.

Soft Delete — Job Row Is Never Hard-Deleted deactivateJob sets is_active = FALSE. The row remains in the jobs table. This preserves referential integrity for future applications rows that reference this job, and allows admin recovery. Candidates browsing jobs filter by is_active = TRUE (Phase 5), so inactive jobs vanish from public listings.

The service-layer check (findCompanyByOwnerId before insert) provides a friendly 409 error; the DB constraint is the hard safety net.
ON DELETE CASCADE — Automatic Cleanup Deleting a user cascades to their company row. Deleting a company row cascades to all its jobs. No manual cleanup code is needed for account deletion. Future applications rows that reference job_id will also cascade.
CHECK Constraints — Defence in Depth job_type IN ('remote', 'hybrid', 'onsite') and experience_level IN ('junior', 'mid', 'senior') are enforced both by Zod enums and PostgreSQL CHECK constraints. The salary range constraint (salary_max >= salary_min) is also duplicated at both layers. A bug bypassing the service can never corrupt the DB.
is_active — Soft Delete Column Jobs are never physically deleted. is_active = FALSE hides them from candidate browsing (Phase 5 will filter on WHERE is_active = TRUE) while preserving referential integrity for application records. A DB index on is_active ensures this filter is cheap.

All Keys Prefixed with prohire: Every Redis key in the application starts with prohire:. This namespaces the application's keys from any other tenants sharing the Redis instance and makes it safe to use glob patterns (redis.keys('prohire:company:jobs:*')) during invalidation without risk of collateral damage.
TTLs as Named Constants — Never Hardcoded All TTL values are defined in src/core/redis/ttl.constants.ts as a typed const object. No magic numbers appear inline in service methods. Changing a TTL in one place propagates to every getOrSet call that uses that constant.
Cache-Aside vs Write-Through ProHire uses cache-aside for reads (getOrSet) and invalidation for writes (not cache-update). On a mutation the stale key is deleted; the next read repopulates it. This avoids the complexity of serialising a write into the exact cache format and is safe even if two writes race — only one DB row is authoritative.
redis.keys() Warning — Not for High-Cardinality Patterns invalidate() uses redis.keys(pattern) which is O(N) and blocks the Redis event loop. It is acceptable here because key counts are small (one key per user/job). In a high-cardinality scenario (thousands of keys), replace with Redis SCAN or a separate key-tracking index. This is noted as a Phase 10 hardening task.

Middleware chain · DTO decisions · resolveCompany pattern

Section 1 — Middleware chain: what each stop does and does not do

Company route middleware chain — full breakdown

Stop What it does What it does NOT do On failure
Express Router Matches HTTP method + path. Selects the middleware array for that route. Runs no middleware itself — it only dispatches. 404 before any middleware if no route matches.
authenticate() Reads Authorization: Bearer <token> header. Verifies JWT signature and expiry. Attaches { userId, email, role } to req.user. Does not check the user's role — only proves identity. Calls next(new AppError(401)) → jumps to global error handler.
authorize("company") Reads req.user.role (set by authenticate). Checks that it is in the allowed roles array. Does not verify the JWT itself — assumes authenticate ran first. Calls next(new ForbiddenError()) → 403 FORBIDDEN.
validate(Dto) schema.safeParse(req.body). On success, replaces req.body with the parsed, type-safe DTO object, then calls next(). Only present on POST/PUT routes. Does not call next(err) on failure — it sends the response directly. Sends 422 VALIDATION_ERROR with field-level error array. Chain stops here.
asyncHandler() Wraps the controller function: Promise.resolve(fn(req,res,next)).catch(next). Any throw inside the controller or service/repo it calls is caught and forwarded. Does not execute any logic itself — it is only an error boundary. Forwards thrown error to global error handler via next(err).
Controller fn Casts req.body to DTO type. Reads req.params and req.user. Calls one service method. Writes JSON response and status code. No business decisions. No SQL. No direct DB or Redis access. Throws a typed AppError subclass from the service — propagates up through asyncHandler.
Service All business logic: ownership resolution, cache reads/writes, invalidation decisions. No req/res access. No direct SQL. Never imports db directly. Throws typed AppError subclasses (ConflictError, NotFoundError).
Repository All parameterised SQL. Returns typed row objects. Ownership is enforced in SQL WHERE clauses. No business decisions. Does not call other repositories. Let DB errors propagate — service or global handler catches them.
Global Error Handler The 4-argument (err, req, res, next) middleware registered last in app.ts. AppError subclasses → formatted JSON. Unknown errors → 500. Never exposes stack traces in production. —
Why authenticate and authorize are two separate middlewares Separation of concerns: authenticate answers "who are you?" (identity), authorize answers "are you allowed?" (permission). Keeping them separate means you can apply authenticate to a route without restricting its role, and you can apply authorize with different role sets on different routes (authorize("admin"), authorize("company", "admin"), etc.) without duplicating identity verification logic.

Section 2 — DTOs: when to create one and why

DTO decision table — all company endpoints

Endpoint Input source DTO? Reason
POST /profile req.body — name, description?, website?, logo_url? ✓ UpsertCompanyProfileDto Body needs Zod validation (string constraints, URL format)
GET /profile none — userId from req.user ✗ — no body, no validate() middleware User identity already validated by JWT. No request body to parse.
PUT /profile req.body — same fields as POST ✓ UpsertCompanyProfileDto Same Zod schema reused for create and update — both require the same validation.
POST /jobs req.body — title, description, job_type, experience_level, etc. ✓ CreateJobDto Body needs Zod validation including cross-field .refine() for salary range.
GET /jobs none — companyId resolved internally from userId ✗ — no body No request body to validate.
GET /jobs/:id req.params.id — single route param ✗ — read directly as string Route params are read as req.params['id']. No body, no validate() needed.
PUT /jobs/:id req.body — all fields optional (partial update) ✓ UpdateJobDto All fields optional but still need type/enum validation + salary cross-field .refine().
DELETE /jobs/:id req.params.id — single route param ✗ — read directly as string Route param only. No body to validate. Soft-delete has no configurable input.
UpsertCompanyProfileDto — Shared Schema for Create and Update Both POST /profile and PUT /profile accept the same body shape and use the same Zod schema. The "upsert" naming reflects this — the schema is not directional. This avoids maintaining two nearly-identical schemas. If the profile shape ever diverges between create and update, split them then.
CreateJobDto vs UpdateJobDto — Why Two Schemas? CreateJobDto makes title, description, job_type, and experience_level required. UpdateJobDto makes every field optional to support partial updates via SQL COALESCE. Merging them into one schema with conditional required fields would require a Zod discriminated union — more complexity for no gain.

Section 3 — The resolveCompany helper: ownership without repetition

resolveCompany — what it is and why it exists

Question Answer
What does it do? Calls companyRepository.findCompanyByOwnerId(userId). Returns the CompanyRow (including company.id). Throws NotFoundError if no company profile exists for this user.
Why not inline the check in each job method? All 5 job methods (createJob, listJobs, getJob, updateJob, deleteJob) need company.id and must fail with 404 if the profile doesn't exist. Inlining duplicates 3 lines × 5 methods = 15 lines of identical logic. A private helper reduces that to one definition.
Why is it private? It is an internal implementation detail of CompanyService. No controller or other service should call it directly — they call the public job methods which call it internally.
Does it hit the DB every time? Yes — resolveCompany is not cached. It is a safety/ownership check that must reflect the latest DB state. Caching it would allow a revoked company profile to still pass the check during the cache TTL window.
What does it enable? All job repository queries are keyed by company.id, not userId. resolveCompany bridges the authenticated user's ID to the company's internal ID in one place.
Pattern: private helper as ownership gate This pattern scales naturally. If a future method needs to verify company ownership before a different kind of operation (e.g. analytics, file upload), it calls resolveCompany first. The ownership check and the ID-translation always happen together, in one place, with one error thrown on failure.
